# 已结算佣金订单退款

用户要求已结算佣金仍可退款，佣金从本次订单退款中扣除。沿用剩余权益折算规则：实际到账 = 扣佣前折算退款 − 本次退款关联订单实际已结算佣金。不是减预计佣金，也不从邀请人账户扣回。

生产订单 24627（`2026102717103834973698873`）本金 10000 分、实发及流水均为 1000 分，仅此一单属于当前订阅。读取时折算 8349 分，因此新规则下为 7349 分，实际预览随时间变化。

实现范围：

- 在原事务与锁内读取全部相关佣金流水，实发字段与流水代表同一笔成本，不相加；只有一个来源有金额时兼容该来源，两者均有正金额而不一致时拒绝异常台账。
- 佣金发放中继续拦截。结算完成不再拦截，扣除实际已发金额；未结算的预计佣金不扣。净退款必须大于零，不能产生负余额入账。
- 将扣佣前金额、佣金扣除总额和逐单扣除证据加入加密报价的状态及退款审计。结算/流水发生变化必须重新预览；同单或合并退款重试仍只入账一次。
- 保留已结算佣金状态与流水、邀请人余额。仅未结算佣金在退款时作废。既有按本金权重分配实际净退款的收据规则继续适用，合并退款只入账一次。
- 后台移除已结算佣金的菜单禁用；预览与退款审计列明扣佣前金额、已结算佣金扣除和实际到账。收据邮件同步列明扣除与实际净退款，旧邮件数据保持兼容。
- 不新增数据库列，沿用已有 JSON 审计与邮件快照。前后端缓存版本同步更新。

验证顺序：先用隔离数据证明旧代码拦截，再覆盖实发/流水来源、重复扣佣、异常台账、零净额、合并退款、独立流量包、报价变更、并发幂等、通知及 HTML 模板；用真实后台假 API 验证已结算菜单和明细。沿用本会话生产发布授权，提交、推送、同提交 CI/双架构镜像成功后备份部署并执行完整生产检查。实际退款仍由管理员在后台确认，本次不代为执行。
