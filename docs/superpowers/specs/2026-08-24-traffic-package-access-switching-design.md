# 流量包权限自动切换设计

## 背景

系统已经按“时效套餐优先、独立流量包补充”的顺序扣减流量，但节点授权仍固定读取 `v2_user.group_id`。因此，用户的基础套餐流量耗尽并开始消耗 180G 不限时流量包后，客户端节点列表和节点端用户授权仍停留在基础套餐权限。

生产配置还存在一处需要同步修正的数据差异：旧版 50 元 180G 流量包套餐属于权限组 3，新版独立流量包目录中的同名商品当前属于权限组 1。目标行为要求两种购买入口都能在流量包生效时获得组 3 权限。

## 目标

- 权限始终跟随当前实际扣减流量的产品。
- 基础套餐有效且有剩余流量时，继续使用基础套餐的权限、限速和设备数。
- 基础套餐耗尽后，切换到最早购买且仍有余额的流量包权限。
- 当前流量包耗尽后，按既有扣减顺序切换到下一份有效流量包。
- 套餐重置、续费或重新购买后恢复可用流量时，自动切回套餐权限。
- 客户端节点下发和节点端用户授权使用相同的持久化权限状态。

## 非目标

- 不合并多个产品的权限组，也不同时展示套餐节点与流量包节点。
- 不改变“套餐流量优先、流量包按购买顺序扣减”的流量核算规则。
- 不修改套餐、流量包的价格、容量、有效期或订单语义。
- 不新增通用的权限叠加、并集或最高等级选择规则。

## 方案选择

采用“事务内同步现有用户权限字段”的方案。

`v2_user.group_id`、`speed_limit` 和 `device_limit` 继续作为节点下发与节点端鉴权读取的有效权限快照。`TrafficPackageService` 负责根据当前流量来源计算并同步这三个字段。这样可复用现有高频节点查询，避免在每台节点轮询用户列表时引入关联产品目录、排序流量包和计算有效来源的复杂 SQL。

未采用的方案：

- 每次节点请求动态计算权限：状态天然准确，但节点轮询查询更复杂，生产数据量下开销和回归风险更高。
- 新增 `active_access_source` 等数据库字段：审计信息更完整，但需要迁移、历史回填和额外一致性维护，超出当前需求。

## 有效流量来源规则

有效来源按以下优先级计算：

1. 用户未封禁，套餐未过期，`transfer_enable > 0`，且 `u + d < transfer_enable`：选择当前套餐。
2. 否则，从 `v2_user_traffic_packages` 中选择 `status = active`、`remaining_bytes > 0` 且 `id` 最小的一条：选择该流量包。
3. 如果没有可用流量包：用户不再具备流量包访问资格；权限快照恢复为当前套餐配置（存在套餐时），否则保持无可用产品状态。

选择最小 `id` 与现有 `consume()` 的 `orderBy('id')` 保持一致，确保“权限来源”和“实际扣减来源”不会指向不同流量包。

流量包的权限配置从其真实来源读取：

- 新版独立流量包：`v2_traffic_packages`。
- 旧版一次性流量包：`v2_plan`。

同步字段包括 `group_id`、`speed_limit` 和 `device_limit`。字段值允许为 `null`，其语义继续沿用现有产品配置。

## 状态切换点

### 流量扣减

`TrafficPackageService::consume()` 已在单用户数据库事务和用户行锁内执行。扣减结束后，在同一事务内重新计算有效来源并同步权限快照：

- 套餐余额仍大于零：保持套餐权限。
- 本次扣减刚好耗尽套餐：切换到第一份仍有余额的流量包。
- 本次同时耗尽一份流量包：切换到下一份仍有余额的流量包。
- 所有余额耗尽：撤销流量包权限快照并恢复套餐配置作为无流量时的基础状态。

### 流量包购买

创建新版或旧版流量包余额后立即重新计算有效来源。套餐仍有余额时不覆盖套餐权限；套餐已经耗尽或失效时立即应用新流量包权限。

### 套餐恢复流量

`TrafficResetService::performReset()` 将 `u`、`d` 归零后，在同一事务内重新同步权限，因此自动恢复套餐的权限、限速和设备数。

套餐购买、续费和升级流程已经写入套餐权限；实现仍会保留该契约，并增加回归测试确保流量包权限不会残留。

### 用户访问兜底

订阅或节点列表请求进入现有可用性检查后，重新同步一次有效权限，用于修复套餐自然过期、历史数据或旧版本部署造成的权限快照滞后。同步仅在三个权限字段实际变化时写库。

节点端用户列表继续读取持久化的 `v2_user.group_id`，流量扣减任务会在套餐耗尽的同一事务中完成切换，因此节点下一次拉取用户列表时使用新的权限组。

## 并发与一致性

- 流量扣减沿用用户行 `lockForUpdate()` 和每用户独立事务。
- 权限来源计算与流量余额更新在同一事务中完成。
- 流量包选择查询在扣减路径中沿用锁定后的余额集合，避免重复查询得到不同顺序。
- 重置路径的用户更新会取得数据库写锁；权限同步包含在同一重置事务中。
- 权限字段没有变化时不执行额外 `UPDATE`，降低节点列表刷新产生的写放大。

## 生产配置修正

发布时单独备份目标商品行，然后将新版独立流量包目录中的“50 元 180G 不限时流量包”权限组从 1 调整为 3。该操作属于生产商品配置，不通过通用代码迁移按名称硬编码修改。

发布验收需要同时确认：

- 旧版一次性 180G 流量包来源仍为组 3。
- 新版独立 180G 流量包来源已为组 3。
- 基础套餐来源仍为组 1。
- 东京高峰专线仍只属于组 2/3。

## 测试策略

新增聚焦回归测试覆盖：

1. 基础套餐有余额时，即使存在 180G 流量包也保持组 1。
2. 基础套餐刚好耗尽后切换到 180G 流量包的组 3、限速和设备数。
3. 第一份流量包耗尽后切换到下一份有效流量包。
4. 套餐重置后从流量包权限切回套餐权限。
5. 新版独立流量包和旧版一次性流量包均能解析其产品权限。
6. 客户端节点列表只返回有效权限组的节点。
7. 节点端用户列表在切换后只向对应权限组节点下发用户。
8. 用户没有任何可用流量时，不因残留的流量包权限获得节点访问资格。

执行现有 Node 回归套件、相关 PHP 语法检查和可用的应用测试。生产发布后使用匿名聚合数据或受控测试用户验证“基础套餐 → 180G → 套餐重置”的完整链路，不输出用户敏感信息。

## 发布与回滚

代码发布遵循现有 Xboard Docker 发布流程：确认工作树和目标提交、备份仓库与配置、等待 CI、更新生产源码、清理缓存，并按队列代码变更范围同时重建 Web 和 Horizon。

由于流量扣减任务位于 Horizon，发布必须同时重建 Web 与 Horizon，避免两者运行不同的权限切换逻辑。

回滚包括两部分：

- 将代码恢复至发布前提交并重建 Web、Horizon。
- 将新版 180G 商品的 `group_id` 恢复为发布前备份值。

无需回滚用户流量余额。用户权限快照可由回滚后的购买、重置或访问流程重新计算；发布前后均需保留权限组分布的匿名聚合快照用于核对。
