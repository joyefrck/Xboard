# 后台用户流量包加量设计

## 背景

后台用户管理的编辑抽屉目前把 `v2_user.transfer_enable` 作为唯一可编辑的“流量”字段。该字段属于用户当前普通套餐，和 `v2_user.u`、`v2_user.d`、`expired_at` 一起构成套餐流量及有效期。

独立流量包余额存放在 `v2_user_traffic_packages`，每次购买都会形成一条独立记录，并通过 `traffic_package_id` 关联 `v2_traffic_packages` 中的流量包商品。用户可以同时持有一个普通套餐和多份流量包；普通套餐与流量包不能合并成同一个商品选择或总量字段。

本次改动需要让管理员在编辑用户时单独发放流量包流量，同时保持普通套餐、套餐到期时间和已经购买的流量包记录不变。

## 目标

- 在用户编辑抽屉中明确区分“套餐流量”和“流量包流量”。
- 管理员可独立选择一个流量包商品，并输入本次增加的整数 GB 数量。
- 每次后台加量新增一条独立的用户流量包记录，不覆盖普通套餐，也不修改历史购买记录。
- 新记录继承所选流量包商品的权限组、限速和设备限制语义。
- 用户同时拥有普通套餐和多份流量包时，继续遵循“套餐优先，流量包按记录 ID 顺序 FIFO”的既有扣减规则。
- 用户列表和编辑抽屉保存后能立即显示新的流量包余额汇总。

## 非目标

- 不允许直接编辑或覆盖所有流量包的汇总余额。
- 不把流量包商品塞入现有“订阅计划”下拉框，也不改变 `v2_user.plan_id` 的单套餐语义。
- 不修改普通套餐的到期时间、重置周期、已用上行或已用下行。
- 不修改已有订单、补建虚拟订单或把后台发放伪装成一次购买。
- 不支持从流量包扣减余额、撤销发放或编辑某一条历史流量包记录；这些能力不在本次范围内。
- 不改变用户端购买流程、商品价格、可售状态或展示状态。

## 方案选择

采用“选择流量包商品并新增独立余额记录”的方案。

管理员提交所选 `traffic_package_id` 和本次增加的 GB 数量。后端验证商品存在后，在 `v2_user_traffic_packages` 新增一条无订单的后台发放记录：

- `user_id`：被编辑用户。
- `order_id`：`null`，表示不是订单购买产生。
- `plan_id`：`null`，避免与旧版一次性套餐混淆。
- `traffic_package_id`：管理员选择的独立流量包商品。
- `total_bytes`：本次输入 GB 转换后的字节数。
- `remaining_bytes`：与 `total_bytes` 相同。
- `status`：`active`。

不采用以下方案：

- 直接改“流量包汇总值”：汇总值来自多条记录，无法安全反向写入，也会丢失权限来源和发放时间。
- 自动增加到最新或最早的已有流量包：用户可能持有多个不同权限的流量包，自动选择容易加错，而且无法给没有有效流量包的用户发放。
- 修改普通套餐 `transfer_enable`：会把加量混进套餐重置和到期语义，不符合两类余额分离的要求。

## 管理端交互

编辑抽屉的流量区域按以下方式呈现：

1. “已用上行”和“已用下行”保持现状，仍表示普通套餐的 `u`、`d`。
2. 现有“流量”字段改名为“套餐流量”，仍编辑 `transfer_enable`。
3. 新增只读“当前流量包余额”，显示列表接口返回的 `traffic_package_remaining`，单位为 GB。
4. 新增“增加流量包”商品选择器，选项来自现有后台流量包目录接口。后台可选择目录中的隐藏或停售商品，因为该操作是管理员发放，不受用户端 `show`、`sell` 限制。
5. 新增“增加流量”输入框，单位为 GB，只接受大于零的整数。

新增字段默认均为空，不会因为打开、查看或保存其他用户信息而重复发放。只有本次同时选择商品并填写增加量时才执行发放。

如果只填写商品或只填写增加量，前端阻止提交并显示成对填写提示；后端仍执行相同验证，不能依赖前端保证数据正确。

保存成功后关闭抽屉并刷新用户列表。刷新后的“流量包流量”列继续显示累计发放/购买总量，“当前流量包余额”使用仍可消费的余额；本次新增记录会计入两者。

## 接口与服务边界

沿用 `POST /api/v2/{secure_path}/user/update`，在现有用户更新请求中增加两个仅用于操作的可选字段：

- `traffic_package_id`：正整数，引用 `v2_traffic_packages.id`。
- `traffic_package_add_gb`：大于零的整数。

两个字段必须同时出现或同时缺失。控制器从用户属性更新参数中移除这两个操作字段，避免把它们传给 `User::update()`。

`TrafficPackageService` 新增一个后台发放方法，职责仅包括：

1. 将整数 GB 安全转换为字节。
2. 创建独立的 `UserTrafficPackage` 记录。
3. 调用现有 `syncAccessProfile()` 重新计算权限快照。

用户普通字段更新与流量包发放放在同一个数据库事务中。任一部分失败时全部回滚，接口返回保存失败，避免出现“用户资料已修改但流量包未发放”或相反的部分成功状态。

## 流量与权限行为

后台发放只新增流量包余额，不修改 `v2_user.transfer_enable`、`u`、`d`、`expired_at` 或 `plan_id`。

发放完成后的权限规则保持现有契约：

1. 普通套餐有效且仍有余额时，继续使用普通套餐的权限组、限速和设备限制；新发放流量包不会提前覆盖套餐权限。
2. 普通套餐耗尽或失效后，使用 ID 最小且仍有余额的流量包作为当前扣减和权限来源。
3. 已有流量包先于新发放记录消费；新记录按其新 ID 自然排在 FIFO 队列末尾。
4. 用户没有可用普通套餐时，发放完成后立即根据当前最早可用流量包同步权限快照。

每次发放都创建新记录，即使选择了用户已经持有的同一商品，也不修改旧记录。这样能保留每次后台加量的数量和创建时间，并避免并发修改某一余额记录。

## 校验与错误处理

- 用户不存在：返回“用户不存在”，不创建记录。
- 商品不存在：返回“流量包不存在”，不修改用户资料。
- 商品与增加量只提供一个：返回“请选择流量包并填写增加流量”。
- 增加量不是正整数：返回“增加流量必须是大于 0 的整数 GB”。
- 字节转换超出数据库 `BIGINT` 安全范围：拒绝请求，不截断数值。
- 数据库写入或权限同步异常：记录服务端错误日志，回滚整个事务并返回“保存失败”。

服务端不能接受客户端提交的权限组、限速或设备限制作为发放依据；这些值始终从所选流量包商品读取，防止请求篡改产品权限。

## 多语言与静态管理端

管理端当前使用已编译静态资产。需要同步修改：

- `public/assets/admin/assets/index.js` 中的用户编辑表单、表单校验、流量包目录请求和提交负载。
- `public/assets/admin/locales/zh-CN.js`、`en-US.js`、`ko-KR.js` 中“套餐流量”“当前流量包余额”“增加流量包”“增加流量”以及校验提示。

不修改用户前台主题和用户端文案。

## 测试策略

后端运行时测试覆盖：

1. 给仍有套餐余额的用户发放流量包后，套餐 `transfer_enable`、`u`、`d`、`expired_at`、`plan_id` 均不变。
2. 新记录关联所选独立流量包，`order_id`、`plan_id` 为空，`total_bytes` 与 `remaining_bytes` 等于输入 GB。
3. 用户已有多份流量包时，新记录单独创建并排在 FIFO 队列末尾，不改写旧记录。
4. 套餐仍有余额时权限保持套餐配置；套餐无可用余额时权限来自最早的有效流量包。
5. 用户普通字段更新和流量包创建任一失败时事务整体回滚。
6. 商品不存在、缺少成对字段、零值、负数、小数和超大数均被拒绝。
7. 未提交加量字段时，原有用户编辑行为不创建任何流量包记录。

静态管理端契约测试覆盖：

1. 表单将原“流量”标为“套餐流量”。
2. 表单展示 `traffic_package_remaining` 的只读余额。
3. 表单包含独立商品选择和整数 GB 输入。
4. 仅在两个字段同时有效时把它们提交给用户更新接口。
5. 中文、英文和韩文文案键完整。

完成后执行相关 PHP 语法检查、流量包运行时测试、管理端聚焦 Node 测试、全量 `tests/*.test.js` 和 `git diff --check`。本次设计不包含生产发布；如后续要求发布，再单独执行 CI、生产备份、容器重建和线上验收流程。
