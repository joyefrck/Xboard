# 后台取消请求提示修复设计

## 背景与根因

生产后台在从订单管理切换到仪表盘时，偶发弹出“未知异常”。同一时段的生产访问日志显示，仪表盘统计、流量排行、队列状态和系统状态接口均返回 HTTP 200；唯一异常是上一页面的 `POST /api/v2/{secure_path}/order/fetch` 返回 499。数据库中约有 9,984 条订单，默认分页查询实测约 15 ms，且 `created_at` 索引正常命中。

后台 Axios 响应拦截器目前会把所有没有 HTTP 响应的错误统一映射为“未知异常”。浏览器取消请求时没有 `response.status` 和后端错误消息，因此正常的页面切换取消被错误地显示成系统故障。

## 目标

- 浏览器主动取消或 Axios 取消的请求不显示错误通知。
- 真实请求超时显示“请求超时，请重试”，不再显示含义模糊的“未知异常”。
- 有 HTTP 响应的认证、权限、资源不存在及后端业务错误保持现有处理方式。
- 不修改后台 API、数据库、订单查询、队列或容器拓扑。

## 实现方案

修改已纳入主仓库管理的后台构建产物 `public/assets/admin/assets/index.js` 中 Axios 响应拦截器：

1. 在显示通知前识别 `axios.isCancel(error)`、`error.code === "ERR_CANCELED"` 和浏览器 `AbortError`。
2. 对取消错误直接返回拒绝的 Promise，让调用方结束原请求，但不产生全局错误通知。
3. 对 `ECONNABORTED`、`ETIMEDOUT` 或超时语义错误显示“请求超时，请重试”。
4. 其余错误继续使用后端 `message`、现有状态码文案或“未知异常”。

不在 `resources/views/admin.blade.php` 中增加 DOM 监听或通知过滤补丁。这类补丁依赖当前 UI 结构，无法从错误源头区分取消、超时和真实网络故障。

## 数据流

正常页面切换时，订单页请求被取消后进入 Axios 错误拦截器。拦截器识别取消类型，跳过全局通知并继续以 rejected Promise 结束调用。仪表盘自身请求正常发起、返回并渲染，不受上一页面取消请求影响。

真实超时时，请求仍进入相同拦截器，但被识别为超时类型并显示明确提示。收到 HTTP 响应的错误继续读取 `response.status` 和 `response.data.message`。

## 测试设计

新增 `tests/admin-request-error-feedback.test.js`，静态检查后台构建产物中的关键行为契约：

- 响应拦截器存在 Axios 取消判断。
- `ERR_CANCELED` 和 `AbortError` 不会进入全局通知分支。
- `ECONNABORTED` 或 `ETIMEDOUT` 映射为“请求超时，请重试”。
- 原有 401、403、404 文案和后端消息优先级仍然存在。

先运行新测试确认当前代码失败，再实施最小修改并确认测试通过。随后运行全部 Node 测试，避免后台构建产物相关回归。

## 部署与验证

生产宿主目录为 `/opt/1panel/apps/openresty/openresty/www/sites/xboard/index`。部署只同步修改后的后台静态资源；由于该资源由 OpenResty 直接提供且响应头为 `Cache-Control: no-cache`，不需要迁移数据库或重建 Horizon。

部署前备份生产上的原始 `public/assets/admin/assets/index.js`，避免覆盖现有无关文件。部署后执行以下验证：

- 比较生产文件校验值与本地修复文件。
- 请求生产 `index.js`，确认取消和超时处理标记存在。
- 在已登录后台从订单管理切换到仪表盘，确认仪表盘数据完整加载且不再出现“未知异常”。
- 检查对应时间段访问日志，确认仪表盘接口保持 HTTP 200。

## 风险与回滚

改动位于压缩后的构建产物，必须使用唯一、精确的字符串替换并由回归测试锁定，避免误改其他代码。若验证异常，立即恢复部署前备份的 `index.js`；该回滚不涉及数据库、缓存、队列或用户数据。
