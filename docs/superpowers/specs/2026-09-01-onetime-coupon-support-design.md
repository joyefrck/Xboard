# 一次性套餐支持优惠券设计

## 背景

当前优惠券验证接口允许一次性套餐通过校验并返回折扣，但订单创建服务在收到 `onetime` 周期和 `coupon_code` 时直接抛出 `Coupon failed`。这导致用户先看到“优惠券验证成功”，点击下单后又看到“优惠券使用失败”。

## 目标

- 所有付款周期为 `onetime` 的旧流量包套餐均可使用优惠券。
- 优惠券仍需满足现有启用状态、有效期、总使用次数、单用户次数、指定套餐和指定周期限制。
- 优惠券折扣计算及使用次数扣减继续在订单事务中完成。

## 非目标

- 不修改独立流量包目录及 `traffic_package_id` 下单流程。
- 不修改一次性流量包到账、流量消费顺序、访问权限同步或订单类型。
- 不增加后台开关，也不修改结算页视觉或交互。

## 方案

删除 `OrderService::createFromRequest()` 中针对 `Plan::PERIOD_ONETIME` 且携带优惠码时的提前拒绝分支。

订单创建继续沿用现有数据流：

1. `PlanService::validatePurchase()` 校验套餐及购买资格。
2. 创建订单模型并写入规范化后的 `onetime` 周期和原价。
3. `OrderService::applyCoupon()` 调用 `CouponService::use()`。
4. `CouponService` 重新校验优惠券，并计算折扣；有限次数优惠券在同一数据库事务内扣减次数。
5. 继续计算会员折扣、订单类型、邀请关系和余额抵扣，然后保存订单。

这样优惠券预校验和实际下单使用同一套业务限制，不再由订单服务额外禁止一次性周期。

## 错误处理

以下既有错误保持不变：优惠券无效、未开始、已过期、次数耗尽、不适用于指定套餐或周期、超过单用户使用次数，以及数据库保存失败。并发下单时仍由事务和 `lockForUpdate()` 保护有限次数优惠券。

## 测试与验收

- 更新流量包回归测试，明确 `OrderService` 不得再包含 `onetime + coupon_code` 的硬拒绝。
- 保留一次性套餐仍按旧流量包路径到账的既有断言。
- 运行聚焦流量包测试、相关测试集合和 PHP 语法检查。
- 检查最终 diff，确认未改变独立流量包、到账、消费和前端逻辑。

## 成功标准

一次性套餐携带符合现有限制的优惠券时可以创建折后订单；不符合限制的优惠券仍由 `CouponService` 返回对应错误；非一次性套餐及不使用优惠券的订单行为不变。
