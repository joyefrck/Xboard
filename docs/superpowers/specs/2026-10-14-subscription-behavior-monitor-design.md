# 订阅行为检测与工单 Telegram 合并告警设计

日期：2026-10-14。状态：2026-10-15 已获用户批准实施并生产启用；检测功能及定时器已启用，验收证据见 docs/operations/2026-10-15-subscription-behavior-monitor.md。

## 目标与范围

每两小时检查订阅访问，发现类似持续脚本下载、反复秒级连发的行为，立即使用现有工单 Telegram 机器人向你指定的用户 ID 3 的已绑定 Telegram 发送通知。同轮多个账号合并为一个消息。通知列出用户 ID、邮箱、当前套餐及实际使用的流量包、异常证据、检查时间范围。

仅检测与通知，不自动封号、重置订阅、修改套餐权限或创建用户工单。排除指定的本人账号 ID 3、已封禁用户和现有管理员/员工账号。无异常不发送例行消息。

## 方案选择

1. 推荐：服务器定时器读取已有 OpenResty 访问日志，运行可解释的规则评分，再通过 Xboard 内的命令解析账号信息和发送通知。可利用历史数据，不修改订阅请求路径，不向业务容器挂载 Docker socket。
2. 备选：在订阅中间件采集结构化事件，使用 Laravel Scheduler 检测。长期扩展方便，但需要改动线上请求路径、增加采集存储，并等待积累新数据。
3. 暂不采用：训练机器学习模型或发送到外部大模型。当前只有少量待核实样本，无法评估精确率；外部模型也无必要接收邮箱或订阅信息。

## 运行与数据获取

- 使用主机 systemd timer，时区 Asia/Shanghai，每个偶数整点执行一次。部署验收后立即运行首轮。任务独立于桌面应用运行。
- 每轮取最近两小时的新行为，并读取最近二十四小时作为连发模式背景；新行为窗口内没有成功下载的用户不因旧记录重复入选。
- timer 使用持久化与互斥锁；恢复运行时根据最近成功检查时间补查，最多回溯二十四小时。执行失败不推进检查时间。
- 从已核实的站点 access.log 及覆盖窗口的轮转文件流式读取，正确处理时区、跨午夜和 gzip；只分析明确的订阅入口。
- PHP 命令提供 user_id 与当前订阅 token 的 SHA-256 映射。原始 token 不离开 PHP 输出边界，不保存映射、完整 URL 或订阅内容到新文件。
- HEAD、重定向、非 200、空响应不计入节点内容下载频率。保留脱敏统计用于解释排除原因。
- 生产来源指标按 access.log 的 peer 地址计数，不参与评分；当前不启用 X-Forwarded-For 信任。已知节点与备用地址不作为“同来源多个账号”的恶意证据。
- 最近七个日历日的计费流量从 v2_stat_user 的日统计读取，覆盖周期套餐和独立流量包，不使用 v2_user.u+d 判断是否仅抓订阅。
- 低流量证据增加全站健康门禁：当前日及昨日的日统计最近更新时间距今不超过 30 分钟，stat 队列最老 ready/reserved 任务不超过 30 分钟。健康不足时流量为未知，不触发 R2；候选个人旧统计不单独视作故障。历史回放仍检查当前管道健康。
- 数据库、日志或 Telegram 配置缺失时报告技术失败，不把缺失数据视为零流量；不发送“无异常”的成功结论。
- 当前 token 映射无法保证识别历史重置前的订阅链接；匹配失败记录单独计数，不归责现有账号。

## 规则模型 v1

告警阈值 70 分。规则和阈值集中配置，消息使用“异常订阅行为”，不推断举报身份。

### R1：持续脚本拉取，80 分

同时满足：

- 最近两小时成功 GET 非空订阅至少 60 次。
- 首末成功下载跨度至少 30 分钟。
- 至少 80% 的成功下载 UA 为通用脚本工具标识，如 curl、wget、python-requests、aiohttp、httpx、Go-http-client。
- 相邻下载间隔中位数不大于 60 秒，至少 70% 的间隔短于 60 秒。

UA 可伪造，此规则证明的是自动化模式，不证明恶意目的。流量使用量作为消息中的背景证据，不要求零流量。

### R2：反复秒级连发与低使用量，70 分

- 最近二十四小时至少出现三个独立连发簇，各簇相隔至少 30 分钟。
- 每个连发簇中，任意滚动 60 秒窗口至少成功下载 10 次，簇内相邻间隔中位数不大于 3 秒。
- 最近两小时至少出现一个符合条件的连发簇。
- 最近七个日历日已记录计费流量不超过 128 MiB。

重复连发 55 分，加上完整、有效的低流量证据 15 分。缺少流量统计、或查询失败时不加低流量分。此规则仍需人工排除客户端重试或操作问题。

### 观察指标

记录成功下载数、活动跨度、间隔中位数、短间隔比例、滚动分钟峰值、连发簇数、UA 家族及可信来源数。普通客户端每分钟/五分钟自动更新、HEAD 测速和单纯多出口访问不单独告警。

## 当前套餐与通知对象

- 收件人只使用用户 ID 3 的 Telegram 绑定；不默认广播给所有员工或其他管理员。
- 2026-10-14 23:57 的只读检查已确认：ID 3 存在且 Telegram 已绑定，工单机器人启用且凭据可读取，6571 已封禁，应用时区 Asia/Shanghai。ID 3 的 is_admin 为 false，因此指定接收人的身份由本次明确授权决定，不依赖该字段；仍将 ID 3 从检测名单排除。
- 使用现有工单机器人凭据。读取凭据后直接调用 Telegram，不在主机脚本、源码、终端、报告或日志中输出。
- 邮箱与套餐名称在实际发送前由 Xboard 查询，主机检测脚本只传账号 ID 与脱敏行为摘要。
- 有可用周期套餐时展示当前套餐；周期套餐不可用但存在有效流量包时展示当前实际流量包，并补充账户原套餐名称，避免把“高级套餐+组 3 流量包”描述为旗舰套餐。
- 在发送前再次核对用户存在、未封禁、非管理员/员工；历史命中账号已被封禁时不发通知。

## 合并、去重和失败处理

- 同轮所有新命中账号一次性合并发送，按分数和异常程度排序，每个账号同时包含邮箱、套餐、命中规则和具体次数/间隔。
- 相同账号与规则在二十四小时内只告警一次；新规则首次命中可再次提醒。仅发送成功后标记已通知。
- 使用锁防止定时任务与手动运行重叠。无异常或全部已去重时不发消息。
- 常规告警使用纯文本消息，避免邮箱、套餐名、UA 中的 Markdown 字符破坏发送。
- 内容超过 Telegram 单条文本容量时，改发一个 UTF-8 文本附件，消息说明异常总人数、检查时间；附件完整列出全部账号信息和行为。仍只有一个 Telegram 消息，不截掉账号，不拆成多条。
- Telegram 明确拒绝或限流时记录失败并保留待发送状态；网络超时等远端结果不确定时记录 uncertain，避免盲目重复发送。日志只输出运行 ID、账号 ID、规则、数量、错误类别，禁止包含邮箱、消息正文、凭据或队列 payload。
- 不修改原有工单通知、注册通知及其他业务 worker 配置。

## 测试与验收

1. 使用合成事件验证 35 秒 curl 持续拉取命中 R1，以及三个独立秒级连发簇+低流量命中 R2。
2. 验证 HEAD、403、301、空响应、每分钟普通客户端更新、五分钟更新、自有节点多账号出口、统计查询失败不产生对应误报。
3. 验证滚动窗口、跨午夜/时区、轮转 gzip、token 重置无法匹配、管理员与已封禁用户排除、同时触发多个规则。
4. 验证同轮多个用户只发送一次；通知字段完整；超长通知以单个附件发送；去重只在确认成功后推进；失败和不确定结果不丢失状态或盲目重复发送。
5. 用生产历史日志 dry-run 回放：6571 的历史行为作为模式验证，正常运行因已封禁应排除；其他账号按真实规则评分，不把调查中的候选直接硬编码为异常。
6. 部署前备份新增/改动文件及 timer 配置，核对现有未提交热修复，保持当前分支与生产修改。
7. 验证 timer 下次运行时间、时区、互斥、重新登录后的持久运行；发送一次明确标注“检测系统测试”的合并测试消息给 ID 3，避免伪造真实异常。
8. 执行 Xboard 发布验收：实际 Horizon 配置、所有业务 worker、三次队列趋势、失败任务、Redis、公网与进程/cgroup 健康；分别报告功能验证、生产启用和消息 API 送达状态。

## 拟定实施文件

- scripts/subscription-behavior-monitor.py：只读日志采集、模型规则与主机运行编排。
- config/subscription_behavior.php：阈值、接收用户 ID、去重窗口与运行设置。
- app/Console/Commands/SubscriptionBehaviorSnapshot.php：输出哈希身份映射及白名单元数据。
- app/Console/Commands/NotifySubscriptionBehavior.php：接收结构化摘要、查询当前账号、调用通知服务。
- app/Services/SubscriptionBehaviorAlertService.php：去重、字段整形、单消息或单附件发送、发送状态。
- deploy/subscription-behavior-monitor.service、deploy/subscription-behavior-monitor.timer：主机持久化运行模板。
- tests/test_subscription_behavior_monitor.py、tests/subscription-behavior-alerts.php：规则与通知行为验证。
