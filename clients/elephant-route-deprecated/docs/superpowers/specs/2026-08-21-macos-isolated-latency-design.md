# macOS 隔离节点测速设计

## 背景与根因

macOS 1.6.5 当前直接调用正在承载 TUN 流量的主 sing-box 内核 `/proxies/<tag>/delay` 接口。同机诊断中，主内核返回的东京节点延迟为 208–256ms；把同一份出站配置放入无 TUN 入站的隔离测速内核后，同一节点为 116–120ms。这证明主内核测速路径受当前 TUN/选中节点影响，不能作为所有节点的首选测速通道。

## 方案比较

1. **隔离测速为主，主内核 API 为兜底（采用）**
   - 每个 worker 使用独立 mixed 入站和 selector，不创建 TUN 入站。
   - 通过 curl 对同一 URL 发起两次完整 HTTP 请求，取两次成功结果中的较小值，避免首次建连预热影响。
   - 隔离内核对某个节点失败时，才调用主内核 `/delay` 对该节点兜底。
   - 优点是延迟口径与 Karing 数值接近，同时保留 AnyTLS 等特殊节点的可用性兜底。

2. **继续使用主内核并对结果除以 2**
   - 实现最简单，但节点、协议和当前选中路径不同时叠加量不是固定比例。
   - 会产生虚假数值，不采用。

3. **仅显示节点入口 TCP RTT**
   - 数值较低，但无法覆盖代理鉴权、节点出口和目标网络，不能判断节点是否真正可用。
   - 不符合现有“可联网延迟”语义，不采用。

## 架构与数据流

`MacosVpnService` 从当前消毒后的 sing-box 配置中选出可测节点，创建 `MacosLatencySession`。`MacosLatencySession` 构建一个临时无 TUN 配置，以最多用户请求的并发数启动 worker；每个 worker 先通过 Clash selector 切到目标节点，再通过本地 mixed 代理运行两次 curl 探测。

成功结果立即推送给 UI。隔离探测失败的节点交给 `MacosLatencyFallbackRunner`，按现有 Cloudflare/GStatic 目标顺序调用主内核 API。结果合并时保持原节点顺序和每个节点唯一的最终状态。

## 异常与生命周期

- 配置缓存读取超时时使用当前活动配置。
- 隔离内核无法启动时，将所有可测节点交给兜底通道，不让整批停在“测速中”。
- 用户再次测速、离开页面或断开加速时，取消当前 generation，终止 curl 子进程并关闭隔离 sing-box 进程。
- 临时目录和端口只属于当次 session，关闭时回收。

## 验收标准

- 主探测成功的节点不再调用主内核 API。
- 主探测失败的节点可由主内核 API 补齐，并向 UI 发送最终结果。
- 隔离 session 失败不会使整批测速失效。
- 取消测速可回收 session 及其所有子进程。
- 实机同一东京节点的隔离测速结果不再包含当前选中节点的叠加时延。
- 应用版本保持 1.6.5，构建新的 arm64 DMG。
